# 给 DeepSeekHarness 的任务书｜M1-A/B 后端与集成

请先读 [协作与防覆写协议](README.md) 和 [项目全貌](../PROJECT_HANDOFF.md)。你可实时读写 GitHub；Gemini 只能读取用户给出的静态快照，用户会把其代码转交给你。你负责验证、集成和上传，不能把转交理解为允许直接覆写。

## 任务 DSH-01：冻结最小接口契约

从最新 main 的干净 worktree 新建 feat/m1-ab-backend 分支，记录实际 SHA。本任务分配时的功能基线是 06088df564033a8903187489d3d1549971ada50d；后续新增的交接文件不是旧快照可以忽略的理由。

先交付 docs/contracts/M1_AB_API.md。至少写清：

- World/WorldDocument/LoreChunk/LoreEntry 最小模型；LoreEntry 可只预留关联结构，不必本批做完整分类 CRUD。
- 世界创建、列表、详情/必要编辑；TXT/MD 文件导入、文档状态/原文预览、按章节读取来源块的接口。
- 请求方法/路径、字段和 TS 对应类型、成功及错误示例、错误码、字符编码、文件名/大小/类型限制、分页和中文来源定位方式。
- 文档删除/重复导入的处理方案；本批不实现的接口明确标为计划，不放假返回让 UI 误判成功。
- M0 localStorage 世界与 M1 真实世界隔离；真实世界尚不能驱动 AI 冒险时，UI 应明确提示。
- 后端地址配置、开发期跨域或代理、请求取消与错误反馈；不要把用户地址或凭据硬编码进组件。

把契约提交 SHA 提供给用户用于发给 Gemini。若 Gemini 提出有根据的冲突，先更新契约，再同步新快照；不要让两端私自形成不同版本。

## 任务 DSH-02：最小后端

允许主要目录：server/**。建议 FastAPI + SQLite + Pydantic；持久层 SQLAlchemy/SQLModel 二选一，优先最小依赖。选型理由和实际版本写入说明。不要在既有前端 package.json 里混装 Python 依赖。

实现世界持久化、TXT/MD 实际上传/解析/原文保存/按标题分块、来源定位、明确的解析状态。成功返回代表数据已提交，失败时不得留下被误认为可用的半成品。导入资料一律当资料，不执行其中指令。默认编码支持范围、无法解码的提示要明确，不静默产生乱码。

本批不接模型、不收 API Key、不做 PDF/DOCX/OCR、自动语义抽取或正式剧情状态机。可记录后续扩展点，不提前完成全部 M1-C/E。中文检索可先提交小规模验证和后续建议，不要误报全文检索已交付。

## 任务 DSH-03：接收 Gemini 与页面接线

Gemini 的文件范围为新增 src/api/**、src/components/documents/**、tests/documents/**、docs/reviews/gemini-*.md。你拥有最终接线文件：src/App.tsx、src/pages/WorldPages.tsx、src/model.ts、vite.config.ts、根依赖与 README 等。

接收流程：
1. 将 Gemini 原包留存于仓库外，读 manifest，核验 base_commit、契约版本、文件哈希和路径范围。
2. fetch 最新仓库，创建 import/gemini-任务号 分支。先查看你自己和他人尚未提交的改动。
3. 对旧文件以基线/最新/产物三方比较；对新增文件检查是否已被别人创建。补丁检查失败时不要强制应用或整包复制。
4. 适用时运行 git apply --check，然后只应用确认的改动。保留 Gemini 作者归属，列出你额外修正的差异。
5. 完成“创建真实世界→选择 TXT/MD→导入→状态反馈→原文/章节预览”的手机路径，并明确区分演示世界入口。保留旧 M0 玩法。
6. 运行后端测试、npm test、npm run build，检查实际手机页面。失败先修复或标明阻塞，再提交 PR。

## 验收与报告

至少覆盖：中文 TXT/MD、标题段落顺序、空/损坏或不支持编码文件、非法格式/超限、同名/重复文档、来源定位、失败状态、服务重启保留、不同世界隔离、演示存档不变、错误输入不丢失。上传限制和重复策略在契约中先声明。

报告路径 docs/reports/deepseekharness-m1-ab.md：基线/契约 SHA、实现路径、启动方式、接口示例、迁移/回滚、测试实际结果、未完成项、Gemini 导入清单、PR/最终提交。不要提交个人真实设定或密钥；测试样本用虚构资料。

不要 force push、reset --hard、整包覆盖、无基线替换文件。main 有新提交时重新合并；冲突不能靠删掉对方代码解决。不自行扩大到 M2–M4。不自动更改站点公开范围；代码合并和线上发布分开报告。Codex 未被另行指派时不会同时编辑你拥有的业务文件，必要时由用户安排复核。
