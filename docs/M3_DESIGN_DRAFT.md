# 一、项目定位

墨境是一套以自然语言为交互方式、以 AI 为叙事与开放式行为推演工具、以程序化规则为基础的开放世界模拟引擎。

核心目标：

让用户导入任意世界观，创建角色，接入自己的 AI 模型，在一个能够持续演化、遵循世界规律、具有长期历史和自主人物的世界中自由生活、探索和行动。

墨境不应只是 AI 小说生成器，也不应只是拥有固定选项的文字 RPG。

我们希望实现：

1. 玩家可以自由决定自己的行动，不受预设剧情路线限制。
2. NPC 拥有自己的生活、目标、知识和行为逻辑。
3. 世界拥有独立于玩家的事件与发展进程。
4. 玩家行动能够真实改变人物、组织、经济和世界历史。
5. 过去发生的事情能够留下长期、可追溯的后果。
6. 不同世界可以采用不同规则，支持不同类型的游戏玩法。

核心设计原则：

**AI 负责创造与推演，程序负责规则、事实、验证和状态管理。**

# 二、当前项目基础与开发约束

当前技术架构：

- 前端：React 19 + TypeScript + Vite + Tailwind CSS
- 后端：Python + FastAPI
- 数据库：SQLite
- 模型：OpenAI 兼容 API
- 手机优先，优先保证安卓浏览器体验。

已经具备的基础：

- M0：本地冒险演示、角色、图鉴、时间线、存档与分支。
- M1：世界资料库、TXT/Markdown/PDF/DOCX 导入、文本分块、检索、人工设定条目和来源引用。
- M2-A：Fake/Live 模型叙事、模型连接、内存 Key 会话、停止与重试。
- M2-B：连续冒险、草案确认、角色基础状态、背包数量账本、世界日志、检查点和分支。

当前仍未完整实现：

- 正式行动规则与复杂因果判定。
- 完整 NPC 自主行为。
- NPC 知识边界与信息传播。
- 远景事件的持续模拟。
- 完整经济和生产系统。

重要约束：

1. 保留 M0、M1、M2 现有功能和数据。
2. 不重建数据库，不清空既有存档。
3. 不将 M0 演示数据自动迁移为正式世界状态。
4. 优先扩展已有 FastAPI、SQLite、模型会话和状态账本。
5. 重大数据库变更采用幂等迁移。
6. 每项功能均应具有自动化测试。
7. 不宣称未实际执行的测试已经通过。
8. 不把全部 NPC 或整个世界的状态塞入模型上下文。
9. 导入世界资料是可信度参考，不是系统指令；必须继续防范提示词注入。
10. 开发采用独立分支和 Pull Request，不直接覆盖 main。

# 三、M3 总体目标

M3 暂定名称：

**Living World —— 动态世界模拟系统**

核心组成：

1. 世界实例与动态状态管理。
2. 世界事件账本。
3. 世界脉动系统。
4. 信息传播与人物知识系统。
5. NPC 自主行为系统。
6. 事件因果传播系统。
7. 通用行动理解与判定系统。
8. 经济、生产及后续玩法模块。

其中世界脉动是可选子系统，不是所有冒险都必须开启的功能。

默认模拟复杂度为标准模式。

# 四、AI 与程序的权责边界

## 4.1 AI 负责

- 理解玩家自然语言行动。
- 分析复杂情境。
- 提出行动方案和可能结果。
- 推演 NPC 的意图、计划与反应。
- 生成世界事件及事件发展提议。
- 分析事件之间的潜在因果关系。
- 根据人物性格和已知信息生成行为。
- 生成自然语言叙事。
- 分析导入的世界观并提出初始世界局势。

## 4.2 程序负责

- 世界状态的最终存储。
- 金钱、物品、体力、时间等账本结算。
- 数据类型、数值范围和结构验证。
- 事件版本、因果引用和时间顺序校验。
- NPC 知识权限控制。
- 事件与人物状态的原子提交。
- 并发控制和请求幂等。
- 后台任务调度。
- 存档、检查点和世界分支隔离。
- API Key 管理与预算记录。

基本原则：

AI 可以提出世界变化，但不能绕过程序直接改写已确认事实。

程序不需要预先穷举所有人类行为。开放式情境可以交由 AI 推演，再由程序检查结果是否合法。

# 五、世界模型：六个基础层次

建议建立以下逻辑层：

## 5.1 Canon Lore：固定世界设定

保存用户导入和确认的基础世界观：

- 地理
- 历史
- 文化
- 人物背景
- 国家和组织
- 物理规律
- 魔法体系
- 已确定的世界规则

原始设定不能被后台模拟静默改写。

AI 可以提出补充设定，但必须区分原始资料、推演内容和已经确认的动态事实。

## 5.2 World State：动态世界状态

保存世界当前实际情况：

- 国家局势
- 城市状态
- 经济和资源
- 组织实力
- NPC 当前状态
- 贸易路线
- 区域关系
- 其他动态事实

## 5.3 Event System：事件系统

保存：

- 主要事件线
- 临时事件
- 事件生命周期
- 事件之间的因果关系
- 已经确认的历史事件
- 事件产生的影响

## 5.4 Knowledge：人物认知系统

保存：

- 人物知道什么
- 人物相信什么
- 人物怀疑什么
- 人物误解什么
- 信息来源
- 信息获取时间
- 信息可信度

必须严格区分世界事实、NPC 认知和玩家认知。

## 5.5 Player Simulation：玩家状态

保存：

- 角色属性
- 金钱
- 背包
- 能力
- 人物关系
- 玩家行动历史
- 玩家所属旅程和分支

## 5.6 World Clock：世界时间

负责：

- 游戏时间
- NPC 日程
- 事件到期时间
- 事件推进
- 旅行与休息
- 后台模拟调度

现实时间与游戏时间必须分离。

# 六、World Instance：独立世界实例

这是 M3 数据架构中非常重要的一项设计。

当前项目已经存在 World 和 Adventure，但动态世界状态不能简单地与所有旅程共享。

建议引入 WorldInstance。

逻辑结构：

World：共享的固定世界观资料。

WorldInstance：某条独立世界历史及其动态状态。

Adventure：玩家在某个 WorldInstance 中进行的冒险。

初期建议一个独立 Adventure 对应一个独立 WorldInstance。

未来可以扩展为多个角色共享同一个 WorldInstance，但不属于当前阶段。

结构示意：

World
- Canon Lore

WorldInstance A
- 动态世界状态
- 事件线
- NPC 状态
- NPC 知识
- 世界时间
- 玩家旅程 A

WorldInstance B
- 动态世界状态
- 事件线
- NPC 状态
- NPC 知识
- 世界时间
- 玩家旅程 B

不同 WorldInstance 之间不得相互污染。

检查点恢复时，应复制对应时刻的动态世界状态、事件、NPC 状态、知识、世界时间和玩家状态，形成新的独立分支。

原路线继续存在，不得被覆盖。

# 七、世界脉动系统 World Pulse

## 7.1 功能定位

世界脉动负责在玩家进行冒险的同时，让世界其他地方持续发生合理的变化。

例如：

- 邻国发生政治变化。
- 商队改变路线。
- 商会扩大经营。
- 某城市出现物资短缺。
- NPC 接受新工作。
- 某组织改变发展计划。
- 远方发生战争或外交冲突。

这些事情并不一定围绕玩家发生。

世界首先独立运行，玩家只是世界中的一个参与者。

## 7.2 世界脉动必须是可选功能

用户可以选择启用或关闭世界脉动。

建议：

- 默认关闭，避免未经用户同意产生额外 API 消耗。
- 可以在创建旅程时选择。
- 后续可以在世界或旅程设置中启用、暂停和恢复。
- 关闭时，普通 AI 冒险功能继续正常运行。
- 关闭时不生成新的后台远景事件。
- 已有事件历史不删除。
- 暂停期间不进行自主世界模拟。
- 重新启用时，从当前世界状态继续，不自动补造一大批暂停期间的历史事件。

世界时间仍然可以随着玩家行动正常推进。

关闭世界脉动不意味着禁止玩家主动触发事件，也不意味着取消已经存在的角色、物品和时间系统。

## 7.3 API Key 与模型配置

推荐为世界脉动提供独立的模型连接配置。

用户可以选择：

A. 使用已有叙事模型配置。

B. 单独配置世界模拟模型：

- API Base URL
- Model Name
- API Key

推荐 B。

独立 Key 的好处：

- 能够在服务商后台单独观察世界模拟 API 消耗。
- 不会与前台叙事调用混淆。
- 可以为世界模拟选择不同的模型。
- 可以单独管理预算和调用频率。

但必须允许用户复用同一个 API Key。

不能强制用户购买第二个模型服务。

安全要求：

- Key 只保存在后端内存会话。
- 不写入 SQLite。
- 不写入 localStorage。
- 不写入存档或导出文件。
- 不写入日志。
- 后端重启后要求重新连接。
- 可以复用当前 M2 模型会话的安全管理思路。

世界模拟模型连接与叙事模型连接应当逻辑独立，即使使用同一个 Key。

## 7.4 世界模拟预算

标准复杂度为默认配置。

建议提供：

- 每轮模拟预算。
- 每次世界脉动最大模型调用次数。
- 每次世界脉动最大 Token 预算。
- 每个游戏日的模拟预算。
- 调用频率和冷却时间。
- 已用 Token 统计。
- 预算耗尽后的暂停或延后策略。

如果服务商返回实际 usage 数据，优先记录实际数据。

如果服务商不返回 usage，只能记录估算值，不能宣称精确账单。

实际费用仍以模型服务商后台为准。

# 八、远景事件机制

## 8.1 主要事件线 Major Threads

长期维持 3～6 条主要事件线。

AI 在创建新 WorldInstance 时，根据世界观资料自动生成初始事件线。

事件线可以来自：

- 国家矛盾
- 地区政治
- 商业竞争
- 组织发展
- 资源争夺
- 技术变化
- 社会矛盾
- 人物计划
- 其他符合世界观的局势

3～6 条是目标范围，不要求每条事件线每轮都必须发展。

事件线允许：

- 正在发展
- 暂时停滞
- 出现转折
- 进入高潮
- 完成
- 失败
- 转化为新的事件线

事件线结束后，可以根据世界情况产生新的事件线。

不能为了填满数量而无意义制造事件。

## 8.2 临时事件 Incidents

临时事件用于短期世界变化。

例如：

- 某个商人临时改变计划。
- 某处道路发生故障。
- 一家商店临时关闭。
- NPC 接到一份特殊订单。
- 某个地方举办集会。

临时事件可以由主要事件线、NPC 自主行为或其他世界状态变化引发。

初期建议限制同时存在的未完成临时事件数量，避免无限堆积。

具体上限可配置。

## 8.3 事件生命周期

每个事件至少包括：

- event_id
- world_instance_id
- title
- description
- location
- scope
- participants
- cause
- current_stage
- created_at_world_time
- updated_at_world_time
- next_update_world_time
- consequences
- knowledge_distribution
- related_events
- source_references
- revision
- status

scope：

- Local：本地
- Regional：区域
- National：国家
- International：国际

事件发展必须保持时间和因果连续性。

## 8.4 玩家不应该自动知道全部事件

必须严格区分：

1. 世界事实：事情实际发生了。
2. 人物认知：哪些 NPC 知道这件事。
3. 玩家认知：玩家通过什么途径得知。

不能因为后台知道一件事情，就直接把它告诉玩家。

# 九、信息传播系统

世界事件需要通过实际渠道传播。

建议支持：

1. 公告和官方文件。
2. 商队与旅人。
3. 书信和使者。
4. NPC 之间的交流。
5. 酒馆传闻。
6. 组织内部消息。
7. 玩家亲身经历。

知识记录至少包括：

- fact_id
- holder_id
- knowledge_type
- content
- source_event_id
- source_person_id
- learned_at_world_time
- confidence
- status

knowledge_type 可以包括：

- confirmed：确认事实
- suspected：怀疑
- rumor：传闻
- mistaken：错误认知

不同人物可以对同一事件拥有不同版本的信息。

信息传播需要考虑距离、交通、渠道、时间和可信度。

远方发生的事情不会立即被本地人物知晓。

玩家只能获得自己有渠道获知的信息。

未来可以增加世界脉动档案：

- 近期消息
- 传闻
- 人物动态
- 地区变化
- 玩家经历的历史

默认不展示全知视角的隐藏事件。

# 十、允许重大历史变化

世界模拟允许产生符合逻辑的重大历史变化。

例如：

- 王朝覆灭。
- 国家分裂。
- 战争爆发。
- 新政权建立。
- 商业势力崛起。
- 技术革新。
- 大规模迁徙。
- 城市衰败。
- 重要组织解体。

但必须遵守：

1. 既定历史不能被静默改写。
2. 未来历史可以通过事件发展改变。
3. 重大变化必须具有合理的因果链。
4. 必须有相应的参与人物、组织和资源条件。
5. 重大事件应有阶段性发展，不能毫无铺垫地瞬间完成。
6. 历史记录应能够追溯事件的起因和发展。
7. 不得违背用户已经确认的世界硬性设定。

AI 可以提出重大事件，但程序需要检查其是否与既有事实、时间和状态冲突。

# 十一、NPC 自主行为系统

NPC 不应该永远停留在原地等待玩家。

每个重要 NPC 应逐步具备：

- 身份
- 性格
- 能力
- 当前目标
- 长期目标
- 当前活动
- 日常安排
- 人际关系
- 资源状态
- 已知信息
- 近期计划
- 行动历史

NPC 的行为必须受到自身知识、资源、能力、时间和地理条件约束。

NPC 不一定与玩家有关。

他们可以为了自身利益、职业、家庭、组织和个人目标行动。

## 11.1 动态模拟深度

采用动态分级：

S 级：当前核心人物。

- 精细模拟目标、计划、关系、知识和日程。
- 与玩家或当前重大事件密切相关。

A 级：重要人物。

- 定期推演。
- 参与区域事件或重要组织活动。

B 级：普通人物。

- 使用简化日程和状态规则。
- 在受到关注时提高模拟频率。

C 级：远方人物。

- 以组织、职业群体和地区状态为主。
- 必要时提升模拟精度。

等级可以动态变化。

NPC 重要性由以下因素决定：

- 与玩家的关系。
- 是否参与重大事件。
- 是否影响当前地点。
- 是否参与玩家当前行动。
- 是否掌握关键资源。
- 最近是否发生重要变化。

不得每轮调用 AI 模拟所有 NPC。

# 十二、事件因果传播系统

事件之间必须能够建立关联。

例如：

邻国提高进口税
→ 商队调整贸易路线
→ 本地材料供应减少
→ 商人改变采购计划
→ 玩家发现材料价格上涨。

事件之间应有明确的来源事件和影响记录。

影响分为：

1. 直接影响：直接改变相关地区、人物、组织或经济状态。
2. 间接影响：暂时不影响玩家，但可能产生后续变化。
3. 独立发展：与玩家暂时无关，属于世界自身的变化。

不能强制所有事件最终都与玩家产生关系。

## 玩家个人状态保护

后台事件可以改变：

- 市场价格。
- NPC 库存。
- 商店经营状态。
- 组织关系。
- 地区资源供应。
- NPC 工作与日程。

但不得随意直接修改玩家：

- 金钱。
- 背包。
- 角色属性。
- 装备。
- 已确认的个人账本。

涉及玩家财产的变化，必须通过正式规则、已确认合同或明确的事件结算机制。

玩家已经确认的交易和历史不能被后台覆盖。

---

# 十三、世界时间系统

游戏时间只由游戏内行动推进。

现实时间不等于游戏时间。

例如：

- 对话：10 分钟。
- 制作：4 小时。
- 休息：8 小时。
- 旅行：数天。
- 长途旅行：数周。

具体耗时由行动规则和情境决定。

用户离线时：

- 世界时间暂停。
- 不继续推进事件。
- 不让 NPC 按现实时间自动生活。
- 不因玩家下线而产生额外游戏时间。

已经排队的后台任务可以在服务器恢复后继续执行，但不能据此推进游戏时间。

后台计算的现实耗时不能自动折算成游戏时间。

---

# 十四、异步世界脉动架构

这是 M3 最重要的技术实现之一。

前台与后台必须分离。

## 14.1 前台玩家行动流水线

玩家输入
→ AI 理解行动
→ 读取相关世界资料和状态
→ 生成结构化行动结果
→ 程序校验
→ 原子提交角色状态与回合
→ 返回叙事。

前台优先保证响应速度。

## 14.2 后台世界脉动流水线

本轮确认提交成功
→ 创建持久化后台任务
→ 前台返回玩家
→ 后台读取世界状态
→ 调度器检查事件
→ AI 生成事件发展提议
→ 程序验证
→ 更新世界状态
→ 更新事件与 NPC
→ 更新知识传播记录
→ 完成任务。

每轮确认后都可以触发一次轻量级检查。

但不要求每轮都进行完整 AI 模拟。

应考虑：

- 游戏时间变化。
- 是否存在到期事件。
- 是否发生重大状态变化。
- 是否有待处理事件。
- 当前预算。
- 上一次脉动时间。
- 当前任务队列状态。

短时间连续行动可以合并模拟。

长时间休息或旅行则应推进更多到期事件。

## 14.3 持久化任务队列

不建议只使用 FastAPI 临时 BackgroundTasks 实现长期任务。

建议在现有 SQLite 中建立持久化任务队列。

任务至少包括：

- job_id
- world_instance_id
- trigger_adventure_id
- trigger_revision
- base_world_revision
- job_type
- payload
- status
- attempts
- created_at
- updated_at
- next_retry_at
- error_summary

任务状态：

- pending
- running
- completed
- failed
- waiting_for_model
- cancelled

需要支持：

- 幂等处理。
- 失败重试。
- 任务恢复。
- 服务器重启恢复。
- 并发锁定。
- 版本冲突检查。
- 任务超时和清理。

不要重复执行已经成功提交的事件。

如果后台模型会话失效，应等待用户重新连接，不得将 Key 保存进任务数据库。

初期不必引入 Redis，优先使用 SQLite 和 FastAPI 应用生命周期内的后台 Worker。

## 14.4 防止前后台状态覆盖

后台任务读取世界状态时记录版本号。

提交前检查相关状态版本。

如果玩家已经改变了相关状态：

- 无冲突的后台变化正常提交。
- 冲突的提议重新校验。
- 必要时重新生成。
- 不得使用旧快照覆盖新状态。

事件提交与相关动态状态更新应尽可能放在同一个短事务中。

AI 网络请求不得放在 SQLite 写事务内部。

# 十五、通用行动系统

这是墨境开放玩法的核心。

玩家可以自由输入：

- 制作物品。
- 寻找工作。
- 交易。
- 交涉。
- 探索。
- 学习。
- 研究。
- 经营。
- 旅行。
- 组织活动。
- 参与政治。
- 其他未预设行为。

行动流程：

玩家输入
→ AI 意图识别
→ 确定行动目标与必要条件
→ 读取相关角色、地点、NPC、物品和世界规则
→ AI 提出行动结果
→ 程序检查资源、能力、时间和规则
→ 结算
→ 生成叙事。

未知行动不能仅仅因为程序没有专门编写该剧情就直接拒绝。

应允许 AI 进行通用情境推演。

但结果必须符合世界规律。

后续专门玩法应建立在统一行动框架之上，例如：

- 职业系统。
- 制造系统。
- 经济系统。
- 商业经营。
- 人物关系。
- 旅行与探索。
- 组织与政治。
- 战斗与冲突。
- 研究和技术。

不要为每一种玩法重新开发独立的游戏引擎。

# 十六、开发阶段规划

## M3.0：世界实例与数据基础

优先级：最高。

- 建立 WorldInstance 概念。
- 区分共享 Canon Lore 和动态世界状态。
- 明确 Adventure 与 WorldInstance 的关联。
- 设计事件、NPC、知识和任务队列数据结构。
- 处理检查点与分支的世界状态复制。
- 制定 SQLite 幂等迁移。
- 保留旧旅程兼容性。

验收：不同旅程、不同分支的动态世界状态完全隔离。

## M3.1：世界事件账本与初始局势生成

- AI 分析世界观资料。
- 自动生成 3～6 条初始主要事件线。
- 事件结构化保存。
- 事件生命周期管理。
- 事件来源引用。
- 临时事件生成与结束。
- 事件版本和因果关联。

验收：创建新世界实例后，可以获得符合世界设定的初始局势。

## M3.2：可选异步世界脉动

- 世界脉动启用/关闭。
- 独立模型连接配置。
- 可复用叙事模型 Key。
- 独立 API 预算。
- 持久化后台任务队列。
- 异步事件推演。
- 事件自动验证与写入。
- 服务器重启恢复。
- 不阻塞前台玩家行动。

验收：玩家结束行动后立即获得反馈，后台能够独立推进事件。

## M3.3：人物知识与信息传播

- NPC 知识记录。
- 事实与传闻分离。
- 信息来源。
- 信息传播渠道。
- 传播时间。
- 玩家认知隔离。
- 消息展示入口。

验收：玩家不能自动知道尚未通过渠道获知的事件。

## M3.4：NPC 自主行为

- NPC 目标。
- NPC 日程。
- NPC 计划。
- NPC 关系。
- NPC 资源。
- 动态模拟分级。
- 与事件系统联动。

验收：重要 NPC 能够在玩家不参与的情况下发展自己的生活和计划。

## M3.5：事件因果与动态经济

- 事件之间的因果关联。
- 地区资源变化。
- 市场供需。
- 商品价格。
- NPC 采购和经营。
- 商业组织行为。
- 事件对玩家周边环境的影响。

验收：远方事件可以通过合理因果链影响玩家所在地。

## M3.6：完整开放行动系统与玩法扩展

- 通用行动解析。
- 行动条件与结果校验。
- 资源和时间结算。
- 职业与技能接口。
- 制作、经营、交易等模块。
- 玩家主动干预世界事件。

验收：玩家可以通过自然语言参与、改变甚至推动世界重大事件。

# 十七、第一条端到端测试场景

建议使用一个规模适中的奇幻世界进行测试。

世界结构：

- 一座北境小镇。
- 两座邻近城市。
- 两个国家。
- 一个大型商会。
- 约十名具有基本身份的 NPC。

AI 自动生成五条初始主要事件线：

1. 本地商业竞争。
2. 区域贸易路线变化。
3. 邻近城市的资源争夺。
4. 国家之间的外交问题。
5. 跨国商会的扩张计划。

玩家在北境小镇经营一家工坊。

模拟过程：

1. 邻国提高进口商品税率。
2. 商队改变运输路线。
3. 本地原材料供应减少。
4. 商人调整采购计划。
5. 玩家发现材料价格上涨。
6. 玩家可以更换供应商、寻找新路线、囤积材料或者不予理会。
7. 玩家行动进一步改变本地经济和事件发展。

这条链路应当贯穿事件、经济、NPC、玩家行动和信息传播系统。

# 十八、M3 第一阶段验收标准

至少满足以下条件：

1. 世界脉动是可选功能。
2. 不开启世界脉动也能正常进行冒险。
3. 新 WorldInstance 可以自动生成主要事件线。
4. 主要事件线能够持续发展和结束。
5. 临时事件可以独立产生和结束。
6. 玩家行动结束后可以异步提交后台任务。
7. 前台不等待后台世界模拟。
8. 后台任务能够在服务器重启后恢复。
9. 世界时间不会因为现实时间流逝而推进。
10. NPC 知识和玩家认知相互隔离。
11. 事件可以产生实际世界状态变化。
12. 后台不能覆盖已确认的玩家账本。
13. 不同世界实例互不干扰。
14. 检查点分支保留独立的动态世界历史。
15. 独立 API Key 与复用 Key 两种模式都可以使用。
16. 能够记录模型使用量或估算用量。
17. 预算耗尽时能够暂停或延后后台模拟。
18. 所有重要事件具有可追溯的来源和版本。
